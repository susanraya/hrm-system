<!-- sdlc:auto:start overview -->
HRM SYSTEM is a two-part application generated by the Quorq AI SDLC platform: a frontend Vite + React 19 single-page app containing every approved screen (currently running on seeded sample data, not live API calls) and a backend Django 5.1 REST Framework service that, since no backend architecture was approved yet, ships with only a health check and no data model. The approved stack targets PostgreSQL 16 and AWS, with Docker Compose provided for local Postgres and a Dockerfile for containerizing the backend.
<!-- sdlc:auto:end overview -->

- Node.js (for Vite 6 / React 19 / TypeScript 5.6 tooling)
- npm
- Python 3.12
- pip
- Docker and Docker Compose (for local PostgreSQL via docker-compose.yml)
<!-- sdlc:auto:end prerequisites -->

<!-- sdlc:auto:start setup -->
1. Clone the repository
2. cd frontend && npm install
3. cd backend && pip install -r requirements.txt
4. From backend/: python manage.py migrate --run-syncdb (creates tables from models.py; no migrations are checked in)
5. Optionally, from the repo root: docker-compose up -d to start a local PostgreSQL 16 instance for the backend
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Frontend API access is centralized in src/lib/api.ts via an apiFetch<T> helper that attaches a Bearer token from VITE_API_SECRET_KEY and reads the base URL from VITE_API_BASE_URL (falls back to http://localhost:8000)
- Generated screens currently render seeded sample data rather than calling the API; wiring a screen to apiFetch is the intended next step per-screen
- Backend ships no migration files; schema changes go into app/models.py and are applied with `migrate --run-syncdb`
- Backend uses pytest with pytest-django (pytest.ini sets DJANGO_SETTINGS_MODULE=config.settings and pythonpath=.) and ruff for linting/formatting
- Frontend uses Tailwind CSS v4 (via @tailwindcss/vite) and TypeScript in strict mode but with noImplicitAny/strictNullChecks disabled
- Frontend testing: Vitest component tests live beside the components they cover under src/, while Playwright e2e specs live in the separate e2e/ directory
- Container runs as a non-root user (appuser) in backend/Dockerfile
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| `npm run build` succeeds locally but deployment/CI fails on type errors | Run `npm run typecheck` (tsc --noEmit) before shipping; `vite build` does not typecheck and can tree-shake out untyped code paths |
| Backend has no tables after a fresh checkout | Run `python manage.py migrate --run-syncdb` -- the scaffold has no migration files, so this generates tables from app/models.py directly |
| `npm run test:e2e` fails to start the backend leg of the webServer | Playwright's config invokes `backend/.venv/bin/python`, so create a virtualenv at backend/.venv and `pip install -r requirements.txt` into it before running e2e tests, or set E2E_BASE_URL to point at an already-running deployment instead |
| Frontend screens don't reflect real backend data | This is expected -- generated screens currently render seeded sample data; wire a screen to the API via the apiFetch helper in src/lib/api.ts to change that |
| `docker-compose up` doesn't start the backend or frontend | docker-compose.yml only defines the `db` (PostgreSQL) service; run the backend and frontend directly with the commands above, or build/run backend/Dockerfile separately |
<!-- sdlc:auto:end troubleshooting -->
